PAI1-mujoco ・ 2026-10-19 の実装

おるすばんアヒルのしくみ

MuJoCo の中のこの家で、見守りカメラなどの家の機器と、二足歩行の小さなロボット (アヒル) と、LLM が手分けして家族を見守る。その中身を、部品ごとに「何をしているか・どう動くか・なぜそうなっているか」で説明する。各節の終わりに、自分で動かして確かめる方法を書いた。

1ひとことで

家に付いている機器がいつも見ている。機器だけでは確かめられないことは、アヒルが近くまで歩いて行って確かめ、声をかける。人の頼みごとは LLM が機器とアヒルの操作に変える。この 3 者を、司令塔という 1 つのプログラムがまとめる。

全部がシミュレーションの中で動いている。家・アヒル・人は MuJoCo (物理シミュレーター) の中にあり、カメラの絵も MuJoCo が描く。家の機器や司令塔は、MuJoCo の外の別々のプログラムで、MQTT という通信でつながっている。

なぜ別々のプログラムにしたか。 本物の家では、カメラ・照明・ロボット・司令塔はそれぞれ別の機械で、ネットワークでつながっている。シミュレーションでも同じ分け方にしておけば、MuJoCo の部分を本物の機械に替えても、司令塔や LLM の側はそのまま使える。

3転倒を追いかける

場面 fall で、ママが居間で倒れてから家族に知らせが届くまでを順に追う。全体で 10 秒ほど (学習した歩き方のとき)。

sequenceDiagram

  participant D as 見守りカメラ (居間)
  participant C as 司令塔
  participant A as アヒル

  C->>C: 横になった人を 3 秒見続けた → 転倒の疑い
  C->>D: 居間の照明をつける (Homie の set)
  C->>A: order: 人のそばへ行き detectObject
  A->>A: 人を見通せる立ち位置を選ぶ → A* → 歩く
  A->>A: 着いたら人の方を向き、頭のカメラ + YOLO

  C->>A: instantActions: speak「大丈夫ですか？」
  1. 人役が倒れる。 時刻表の t=30 の行を見て、ママの人形を居間の床に横向きに置く。人は物理で動く体ではなく「置物」で、置き場所と向きを書き換えるだけ。home/scenario.py
  2. カメラが撮る。 sim_server が居間の天井の角のカメラで 640×480 の絵を MuJoCo に描かせる。5 台まとめて YOLO にかける。home/devices.py
  3. 位置と姿勢を出す。 人の枠の下端を床の上の点に直し (足元)、枠の形から「横になっている」と判断する。home/perception.py
  4. MQTT に出す。 homie/cam-ima/camera/persons に [{"x":5.8,"y":1.2,"posture":"lying",...}] を出す。
  5. 司令塔が疑う。 同じ場所の「横になった人」を 3 秒以上見続けたら転倒の疑いとする。1 回だけの誤検出で騒がないため。
  6. 照明をつけ、アヒルに頼む。 homie/light-ima/light/on/set に true。アヒルには VDA 5050 の order で「この点のそばへ行き、人を探せ (detectObject)」と頼む。
  7. アヒルが行く。 人の真上には立てないので、人から 0.8〜1.3 m で、間に家具がない立ち位置を選び、地図の上で経路を作って歩く。
  8. アヒルが確かめる。 人の方を向き、頭のカメラ (床から 24 cm) の絵を YOLO にかける。横になっている人が見えたら結果を返す。
  9. 知らせる。 司令塔は結果を見て home/alerts に転倒を出し、アヒルに「大丈夫ですか？ご家族に知らせました。」と話させる。アヒルが見ると立っていたら、誤報として取り消す。
確かめる

場面を 1 回通し、出来事の時刻を見る。--viewer を付けると MuJoCo の画面でも見られる。

uv run python app/run_scenario.py --scenario fall --speed 1 --viewer

別の端末で MQTT に流れるものを覗くと、4〜9 の順にメッセージが出るのが見える。

uv run python app/mqtt_watch.py

4家

家は手で描いていない。間取り図を読み取った houses/home/layout.yaml から、sim/house.py が MuJoCo の形式 (MJCF) を毎回作る。

マス目で書く

日本の家は半間 (0.91 m) の倍数で設計されている。間取り図に半間のマス目を重ねると、壁がほぼマス目の線に乗る。そこで YAML の座標はマスの数で書き、作るときに 0.91 を掛けて m にする。

- {name: ima, label: 居間, level: 1F, rect: [4, 9, 0, 4], material: tatami}   # x 4〜9、y 0〜4 マス
- {level: 1F, seg: [4, 4, 12, 4], openings: [{at: [7.2, 8.9], door: ima}, ...]}   # 壁と扉の開口

確かめ方として、居間 8 畳が 4×4 マス (3.64 m 四方) になり、1 階と 2 階のマスの合計 101 マス ≒ 83.6 m² が、記事の推定床面積 83.83 m² と合う。

作られるもの

  • 床: 1 階は地面から床までの箱。玄関の土間は 20 cm 低い箱にしたので、段差がそのまま形になる (アヒルは降りられない)。
  • 壁: 線分を扉と窓のところで切り分けた箱。扉の上 (2.0 m から上) は壁、窓は 0.9〜2.0 m がガラス。
  • 扉: 開き戸は回る関節、引き戸は滑る関節を持つ体。IoT で開け閉めするときは関節の角度を書き換える。
  • 階段・家具・天井・屋根・照明 (7 灯)・見守りカメラ (5 台)。
表示のグループ。 MuJoCo の形には見せ方の番号 (group) を付けられる。1 階は 0、2 階は 4、天井と屋根は 5 にした。見下ろしの絵では 4 と 5 を隠すと 1 階の中が見える。人を 2 階に置くと人のグループも 4 に変えるので、1 階を見下ろしたときに 2 階の子どもが浮いて見えない。
扉は押されても動かない。 扉の関節は物理で自由に動くので、立っている人の当たり判定に押されて閉まりかけ、アヒルが応接室に入れなくなったことがあった。今は毎ステップ、決めた角度に戻している。
確かめる

家を上から・斜めから・各カメラから描いて build/house/ に保存する。layout.yaml のちゃぶ台の rect を書き換えてもう一度描くと、家が YAML から作られていることが分かる。

uv run python spike/house_views.py

5アヒルの体と歩き方

アヒルは Pollen Robotics の Microduck (高さ約 25 cm、サーボ 14 個)。形のデータ (MJCF とメッシュ) は公開リポジトリ microduck_rl から取ってくる。

歩き方は学習済みの方策

二足歩行の関節の動かし方は、人が式で書いたものではなく、強化学習で作られたニューラルネット (方策) が決めている。方策は ONNX という形式のファイルで、sim/duck.py が 1 秒に 50 回これを呼ぶ。

方策に渡すもの (観測、61 個の数)数
胴体の回る速さ (ジャイロ)3
胴体から見た重力の向き (傾き)3
14 関節の角度 (立った姿勢からの差)14
14 関節の角速度14
前回の出力14
指令: 前・横の速さと回る速さ 3、頭の向き 4、胴体の姿勢 613

方策が返すのは 14 関節の目標角度 (立った姿勢からの差)。サーボの中の制御 (BAM という実物のサーボを真似たモデル) が、その角度に向けてトルクを出す。MuJoCo は 5 ms ずつ 4 回進めて、次の 0.02 秒へ。

使う側は「速度指令」を出すだけ。 経路をたどるプログラムは、関節のことを何も知らない。「前へ 0.3 m/s、左へ 0.5 rad/s 回れ」と指令を出すと、方策がそれに合う歩き方を作る。ただし指令どおりの速さは出ない (公開の方策では指令の 1/3 ほど)。だから経路をたどる側は、毎回いまの位置を見て指令を直し続ける。

頭のカメラ

元のデータのカメラは、設計ソフト (Onshape) の座標のままで、後ろ上を向き、絵も 90° 回っていた。MuJoCo のカメラの約束 (−z が視線、y が上) に合うよう回し、広角 (75°) で少し上向き (10°) にした (sim/scene.py の add_duck)。

確かめる

速度指令を出したとき、実際にどれだけ進み、どれだけ回るかを方策ごとに測る。

uv run python learning/eval_gait.py --policy velstand --policy duck_walk

6地図と経路

LiDAR は使っていない。家の形は間取りから分かっているので、地図はそこから作る。

地図 (sim/floormap.py)

  • 1 階を 5 cm のマスに分ける。
  • 「通れる床」は、上面が 1 階の床の高さにある床の形 (土間や外は入らない)。
  • 「障害物」は、アヒルがぶつかる高さ (床から 1〜35 cm) にかかる形すべて。壁・家具・閉じた扉・人。MuJoCo のモデルから直接作るので、扉を開け閉めしたり人が動いたりしたら作り直す。
  • 障害物からの距離を計算し、アヒルの半径 + 余裕 (15 cm) より近いマスは通れないことにする。壁から 30 cm 以内は少し通りにくい (費用を足す) ので、廊下の真ん中を通りたがる。

経路 (A*)

A* でマスをたどる最短の道を探し、見通せる点は飛ばして曲がり角だけの経路にする。目的地のそばへ行けない (人や家具でふさがれている) ときは、歩いて行ける所のうち目的地に一番近い所まで行く。

経路をたどる (pure pursuit、sim/navigator.py)

  • いまの位置を経路の上に落とし、経路に沿って 30 cm 先の点を狙う。
  • 向きが 0.7 rad (約 40°) 以上ずれていたら、止まってその場で回る。合っていれば進みながら向きを直す。
  • 12 秒たっても 10 cm も進まず向きも変わらなければ「詰まった」として、いまの位置から経路を作り直す (3 回まで)。

人を見る立ち位置

人を確かめに行くとき、行き先は人そのものではない。人から 0.8〜1.3 m の通れるマスのうち、人までの線の近く (15 cm) に家具がなく、歩いて行ける場所で、歩く距離が短いものを選ぶ (viewpoint)。最初はちゃぶ台越しに人を見ていて、頭のカメラの視界がふさがれていたのでこうした。

確かめる

居間 → DK → 応接室 → 洗面所と歩かせ、地図と経路の絵 (build/nav/map_*.png) と動画を残す。白が通れる所、灰色が壁に近い所、赤線が経路。

uv run python spike/nav_test.py

7カメラで人を見る

YOLO は絵の中の人を四角い枠で囲むだけで、床の上のどこにいるかは教えてくれない。そこで、カメラの位置・向き・画角 (MuJoCo のモデルから読む) を使って、枠を床の上の点に直す (home/perception.py)。

足元の位置

枠の下端の真ん中の画素を通る視線をカメラから伸ばし、床 (高さ 0) とぶつかる点を足元とする。ピンホールカメラの式で、画素から視線の向きを出せる。

立っているか、横になっているか

天井のカメラ (高さ 2.3 m) では、枠の上端の視線も床まで伸ばす。

  • 横になった人なら、上端の視線は体の向こう側の床に落ちる。下端との距離は身長くらい (2.6 m より短い)。
  • 立っている人なら、上端の視線は頭の上を通って、ずっと遠くの床に落ちる (4 m 以上)。
  • ただしカメラの真下近くの人は縮んで見えて距離が短くなるので、「足元に立てた板の上で頭の高さが 1.5 m 以上なら立っている」も使う。

アヒルの頭のカメラ (高さ 24 cm) では、この方法は使えない (上端の視線が上向きで床に届かない)。代わりに体の上端の高さを測り、80 cm より低ければ横になっているとする。横になった人の位置は、足元ではなく体の真ん中 (上端と下端を床に落とした点の中点)。

学習したモデルでは姿勢はクラスで決まる。 追加学習した YOLO は、枠と一緒に「立っている人 / 横になっている人」を答える。今はそれがあれば姿勢はそちらを使い、上の幾何の判定は位置を出すのに使う。

最後に、推定した位置はそのカメラの部屋の中 (壁から 25 cm 内側) に収める。壁際の人は壁の向こうに推定されることがあるため。

確かめる

人を置いてカメラで撮り、推定と正解を並べて出す。絵は build/perception/。

uv run python spike/perception_test.py

8MQTT と Homie (家の機器)

MQTT は、ブローカーという中継役を通して「トピック (住所)」ごとにメッセージを配る通信。出す側は相手を知らなくてよく、欲しい側がトピックを購読する。+ と # で複数のトピックをまとめて購読できる。

Homie は、家の機器を MQTT でどう表すかの決まり。機器・ノード・プロパティの 3 段で、値の型や書き込めるかどうかも MQTT に出す。

homie/light-ima/$name                 照明 (居間)
homie/light-ima/light/on/$datatype    boolean
homie/light-ima/light/on/$settable    true
homie/light-ima/light/on              true          ← いまの値
homie/light-ima/light/on/set          false         ← ここに書くと消える
homie/cam-ima/camera/persons          [{"x":5.8,"y":1.2,"posture":"lying",...}]

家の機器は、見守りカメラ 5 台・人感センサー (部屋ごと)・照明 7 灯・スマートロック 2 つ (と扉の開閉センサー)・スマートスピーカー 3 台。人感センサーは、人役がその部屋にいるかどうかから値を出している (本物の焦電センサーの代わり)。

なぜ決まりに合わせるか。 型や書き込めるかが MQTT に出ているので、受け取る側は機器ごとの説明を手で書かなくてよい。後で出てくる WoT の説明書も、この Homie の記述から自動で作っている。
確かめる

家を動かしたまま、照明だけ、カメラだけを覗く。照明を手で消してみる。

uv run python app/start_home.py
uv run python app/mqtt_watch.py "homie/+/light/#"
uv run python app/wot_cli.py call light-ima__set__on '{"value": false}'

9VDA 5050 (アヒルへの指示)

VDA 5050 は、工場の無人搬送車 (AGV) と、それを動かす管理システムの間の決まり。MQTT の上で動く。家のロボットにもそのまま当てはまる部分が多いので使った。

トピック向き中身
…/order司令塔 → アヒルノード (行き先) とエッジ (道) の列。ノードには着いたらすること (action) を付けられる。
…/instantActions司令塔 → アヒルいますぐすること。話す、一時停止、order の取り消し。
…/stateアヒル → 司令塔位置、歩いているか、どのノードまで来たか、各 action の状態 (WAITING / RUNNING / FINISHED / FAILED) と結果。1 秒ごと。
…/factsheetアヒル → 誰でもできること一覧 (どの action をどんな引数で受け付けるか、最高速度など)。

トピックの頭は uagv/v2/OrusubanHome/microduck-01/。使っている action は detectObject (VDA 5050 で決まっている「物を探す」。ここでは人)、speak (この家で足した「話す」)、wait。

アヒルが経路を考える。 order にはノード (行き先) だけを書く。途中の道はアヒルが自分の地図で考える。ノードの allowedDeviationXY (この距離まで近づけば着いたとする) を使って、「人のそばまで」を表している。
アヒルに指示を出すのは司令塔だけ。 VDA 5050 では、1 台のロボットに order を出す管理システムは 1 つという前提。LLM がアヒルを動かしたいときも、直接 order を出さずに司令塔に頼む。
確かめる

アヒルとのやりとりだけを全部見る。--all を付けると 1 秒ごとの state も出る。

uv run python app/mqtt_watch.py "uagv/#" --all

10司令塔 (決まりごとと仕事)

app/coordinator.py は 0.05 秒ごとに「決まりごと」を順に見て、必要ならアヒルの「仕事 (Job)」を作る。アヒルは一度に 1 つの仕事しかしないので、仕事は優先度の順に並ぶ (転倒が一番先)。

決まりごと見るものすること
転倒見守りカメラの「横になった人」3 秒続いたら照明をつけ、アヒルに確かめさせ、結果で知らせる / 取り消す。寝室の布団の人は除く。
起床家の時計 (7:00) と、子ども部屋のカメラ布団で寝ていたら、部屋の照明とスピーカー、アヒルが階段の下から呼ぶ。30 秒ごとにもう一度、それでも起きなければママ (1 階で立っている人) に知らせに行く。起きたら取り消す。
玄関鍵と扉の開閉センサー扉が開いたらアヒルが見に行き、人がいれば「おかえりなさい」。閉まって 20 秒鍵が開いたままなら施錠。
照明人感センサーと照明だれもいない部屋の照明を 60 秒で消す。人が来たらつける。
依頼home/coordinator/requestsWoT (LLM) からの「部屋へ行く・部屋を確かめる・戻る」を仕事にし、終わったら結果を返す。

仕事は「行く (order を出す)」「話す (instantActions)」「関数を呼ぶ」の手順の列。「行く」では order の最後に短い wait を付けておき、それが FINISHED になったら次の手順へ進む。

時刻はシミュレーションの時刻。 司令塔は MuJoCo の外にいるので、sim_server が毎秒出す home/time と home/clock を時計にしている。シミュレーションを速く回すと司令塔の反応が相対的に遅く見えるので、比べるときは速さを実時間の 2 倍に揃えた。

11WoT と LLM

W3C WoT Thing Description (TD) は、機器の説明書を JSON で書く国際標準。「この機器には何の値があり (properties)、何ができ (actions)、どこにどう頼めばよいか (forms)」が書かれる。

説明書は手で書かない

  • 家電の TD は、MQTT に出ている Homie の記述から作る。書き込めるプロパティは書ける (readOnly: false) になる。
  • アヒルの TD は、VDA 5050 の factsheet (できること一覧) と、司令塔に頼める仕事 (部屋へ行く・確かめる・戻る) から作る。
  • 作った 30 台分の TD は、W3C の公式の JSON Schema で検証している (/things/validate)。

説明書から LLM の道具を作る (home/wot_tools.py)

TD の action           → 道具 robot__checkRoom(room)
TD の書けるプロパティ   → 道具 light-ima__set__on(value)
読めるプロパティ        → 道具 read_property(target)
道具を呼ぶ             → TD の forms に書かれた URL と HTTP の種類で wot_server を呼ぶ

LLM は道具の説明を読み、頼みごとに合う道具を選んで引数を入れる。たとえば「応接室の様子を見てきて」なら robot__checkRoom({"room": "ousetsu"})。wot_server はそれを司令塔への依頼に直し、アヒルが行って確かめ終わるまで待って結果を返す。

LLM の役は 3 通りに入れ替えられる。どれも同じ道具を使う。

  • app/llm_agent.py: Claude の API (有料、1 回 2〜4 円ほど)。
  • app/wot_mcp.py: 道具を MCP サーバーとして出し、Claude Code が使う。このフォルダで Claude Code を開くと道具が見える。
  • app/wot_cli.py: コマンドで道具を見たり呼んだりする。Claude Code のセッションから使える。
確かめる

家を動かしたまま、TD を見て、道具の一覧を出し、道具を 1 つ呼ぶ。

uv run python app/start_home.py
curl http://127.0.0.1:8080/things/robot
uv run python app/wot_cli.py list
uv run python app/wot_cli.py call robot__checkRoom '{"room": "ousetsu"}'

12学習 1: YOLO を家に合わせる

公開の YOLOv8s は、たくさんの写真 (COCO) で人を見つけるよう学習済み。でも横になった人や、床すれすれの低い視点の絵は苦手で、居間以外で倒れた人を見逃していた。そこで、この家の絵で追加学習した。

正解付きのデータを自動で作る (learning/make_dataset.py)

  1. 人 2 人を家の中のランダムな場所・向き・姿勢 (立つ / 横になる) に置き、照明をランダムにつけ消しする。
  2. 見守りカメラ 5 台とアヒルの頭のカメラ (人の近くのランダムな場所) で撮る。
  3. 同じ視点で「どの画素がどの物か」の絵 (セグメンテーション) も描く。人の画素を集めた外接する箱が、正解の枠になる。人が描き込むラベル付けは要らない。

2000 場面で 7119 枚 (立っている人 3076 人、横になった人 4471 人)。学習 8 : 検証 1 : テスト 1 に分けた。公開の YOLOv8s から始めて 2 クラスで 30 エポック、RTX 3060 で約 50 分。

13学習 2: 歩き方を強化学習する

公開の歩き方 (velstand) は、この家の MuJoCo では指令の 1/3 ほどの速さでしか進まず、駆けつけるのに時間がかかっていた。そこで Microduck の学習用の仕組み (microduck_rl) を使い、自分の GPU で歩き方を学習し直した。

しくみ

  • 強化学習 (PPO): アヒルに歩かせてみて、「指令の速さについてこられた」「転ばなかった」などで点 (報酬) を付け、点が上がるように方策を少しずつ直す。これを何千回も繰り返す。
  • 4096 匹を同時に: mjlab (MuJoCo Warp) は MuJoCo を GPU の上で動かすので、4096 匹のアヒルを同時に歩かせて経験を集められる。
  • タスクは公開のもの (Mjlab-Velocity-Flat-Backlash-MicroDuck) をそのまま使い、報酬などは変えていない。Docker (GPU 付き) で 1500 回更新、約 2.5 時間。
指令公開 velstand学習した duck_walk
前へ 0.4 m/s0.142 m/s0.343 m/s
前へ 0.3 m/s0.096 m/s0.111 m/s
前へ 0.2 m/s 以下ゆっくり進む足踏み
回る 1.0 rad/s0.96 rad/s0.48 rad/s

速いが、小さい指令では足踏みになり、回るのは遅い。そこで方策ごとに前進の指令の上限と下限を決めた (sim/world.py の POLICY_SPEED。duck_walk は 0.32〜0.4)。転倒の知らせまでの時間は、居間 15.6 → 11.0 秒、応接室 40.6 → 23.6 秒、DK 53.8 → 29.6 秒になった。

公開の方策より速くなった理由は、はっきりとは分かっていない。公開の方策は別のタスク (歩く・立つ・起き上がるを 1 つで、でこぼこの床) で学習されていて、その違いが考えられる。

確かめる

学習曲線 docs/learning/rl_curve.png を見る。歩き方を替えて同じ場面を回す。

uv run python app/check_scenarios.py --only fall_dk --policy velstand
uv run python app/check_scenarios.py --only fall_dk --policy duck_walk

14本物との違い (シミュレーションで省いたこと)

  • アヒルの位置: アヒルは自分の正確な位置を MuJoCo から教えてもらっている。本物では、室内の電波測位 (UWB など) や、見守りカメラでアヒルを見つける、足の動きから位置を数える、などが要る。
  • 人: 置物で、姿勢は「立つ」と「横になる」だけ。歩く人は、立った形のまま滑らせている。座る・しゃがむ姿勢はない。
  • 人感センサー: 人役がその部屋にいるかどうかから値を作っている。
  • 学習した YOLO: 同じ人の形と同じ家の絵で学習・評価した。実物の写真での精度は分からない。
  • 階段: アヒルは上れない。2 階は機器だけで見守り、アヒルは階段の下から呼ぶ。
  • 扉: アヒルは扉を開けられない。開いている扉だけを通る。

16用語

MuJoCo
物理シミュレーター。体と関節、ぶつかり、カメラの絵を計算する。
MJCF
MuJoCo のモデルを書く形式 (XML)。家は YAML から、アヒルは公開のファイルから作る。
方策 (policy)
観測を入れると行動 (関節の目標角度) を返すニューラルネット。強化学習で作る。
ONNX
学習したニューラルネットを保存する共通の形式。学習した道具 (PyTorch) と使う道具が違っても読める。
PPO
強化学習の方法の 1 つ。方策を一度に大きく変えすぎないように少しずつ直す。
A*
地図の上で最短の道を探す方法。ゴールまでの見込みの距離を使って、探す範囲を絞る。
pure pursuit
経路の少し先の点を狙い続けて、経路をなめらかにたどる方法。
YOLO
絵の中の物を四角い枠とクラス (人など) で答えるニューラルネット。
mAP50
検出の精度の指標。正解の枠と 50% 以上重なれば当たりとして、見逃しと誤検出の両方を数える。
セグメンテーション
画素ごとに「どの物か」を塗り分けた絵。MuJoCo は正確に描けるので、正解の枠がただで手に入る。
MQTT
トピックごとにメッセージを配る通信。ブローカーが中継する。
Homie
家の機器を MQTT でどう表すかの決まり (機器 / ノード / プロパティ、型、書き込めるか)。
VDA 5050
無人搬送車と管理システムの間の決まり。order・instantActions・state・factsheet。
W3C WoT TD
機器の説明書を JSON で書く国際標準。値・できること・頼み方を書く。
MCP
LLM のアプリに道具を出すための決まり。Claude Code はこれで外の道具を使える。
